# Game Design Spec — 구현자 피드백 (self-questioning review)

Status: **feedback / 질문 목록** — 작성: gameplay-foundation 슬라이스 구현자.
대상: `docs/design/game-design.md` (DRAFT).
규칙: 여기서 **F1~F8은 서로 충돌하는 확정문**이라 코드를 쓰기 전에 어느 쪽이
정본인지 정해야 한다. **Q1~Q10은 미결/미정의라 코드에 `// 미결:` 스텁으로만
남긴다.** 이 문서는 결정을 대신하지 않는다 — 결정 없이 구현하지 않는다는
spec 규칙(§표기 규칙 "미결")을 지키기 위한 목록이다.

이 슬라이스에서 채택한 임시 해석은 "구현 해석"에 적고, 사용자가 반박하면
코드를 그쪽으로 고친다.

## A. 서로 충돌하는 확정문 (구현 전 해소 필요)

### F1. 파티 전멸 시 "진행 초기화" vs "클리어한 던전 체크포인트"

- §1 장르: "파티 전멸 = **런 종료 + 진행 초기화**. 남는 것은 명단과 해금 풀뿐이다 (§6)."
- §2 진행 체크포인트 (사용자 수정 m00732): "던전 1개를 클리어하면 다음 런은 그 다음
  던전에서 시작할 수 있다… 되돌아가는 지점은 **클리어한 던전 개수**다."
- §2 실패와 재시작: "남는 것은 §6의 L1/L2/L3, **클리어한 던전까지의 진행도**, 그리고 장비 창고다."

두 서술이 정면 충돌한다. §1은 "진행 초기화", §2는 "클리어 던전까지 유지".
또 §1은 "남는 것은 명단과 해금 풀뿐"이라 장비 창고도 부정하는데 §2는 유지한다.

**구현 해석(임시)**: §2 (m00732, 더 나중·구체적)를 정본으로 본다. 전멸 시
소실 = 현재 던전에서 얻은 파편·수치노드·룬 + 런 스코프 EXP. 유지 = 클리어한
던전 수(= 다음 런 시작 던전), 장비 창고, 캐릭터 레벨·해금. §1의 한 줄은
stale로 표시하는 편집이 필요하다.

### F2. 장비 영속 vs 장비 런 스코프

- §2 장비 이월: "**확정 = B, 사용자 결정 m00738**: 장비는 영속이며 획득 장비가 계속 누적된다."
- §5 요소 스코프: "거점에서 정하고 런에 들어가는 것 (영속): … **장비 창고** — 장비는 영속".
- §9 결정 이력: "장비 영속 안 → **폐기**. 이유: 초반 던전이 너무 쉬워진다. **장비는 런 스코프.**"
- §9 결정 이력(같은 목록 뒤): "**장비 이월 형태 = B(완전 영속)** (§2, 사용자 결정 m00738)."
- §9: "강화 요소의 스코프 확정(§5): … **런 종료 시 초기화 = 장비 + 수치노드 + 룬**."

§9 한 절 안에 "장비는 런 스코프(폐기됨)"와 "장비 = B 완전 영속(확정)"이 같이 있다.
또 §5 표의 "런 종료 시 초기화되는 것" 목록에도 장비가 빠져 있고 §9의 확정 요약에는
장비가 들어간다.

**구현 해석(임시)**: m00738(= 최신 사용자 결정)을 정본으로 본다. **장비 영속 +
창고 누적, 런에는 장착 세트를 반입.**

### F3. 장비 영속의 균형 가드 부재 (F2의 결과)

§9는 장비 영속을 택한 이유로 "상위 던전 난이도가 오르므로 강화를 들고 가는 편이
진행 곡선과 맞다"고 쓰고, 같은 문서 §6은 안전 기준을 "1번째 런과 20번째 런의
승률 차 10~20%p 이내"로 못박는다. 장비가 영속·누적이면 "시작 파워"가 계속 오르고,
이를 막던 가드("장착 장비에서만 노드 포인트 산출")는 m00798에서 폐기됐다.
즉 지금 문서에는 장비 누적을 통제하는 장치가 **하나도 없다**.

**질문**: 상한이 (a) 던전 깊이 대비 장비 티어 곡선, (b) 창고 슬롯/장착 제한,
(c) 어픽스 풀 제한 중 무엇인가? 결정 전까지 장비는 "창고에 쌓이고 장착 세트를
반입한다"까지만 구현하고, 파워 상한 로직은 `// 미결(design §6): 장비 누적 상한`으로 남긴다.

### F4. §6.1 손실 장치의 "미결" 표시가 stale

§6.1 제목은 "**확정: 런 자체가 투자 하나만 사용**", 본문은 "후보 1만 채택",
그런데 마지막 줄은 "**미결**: 위 후보 중 채택 조합." 이미 채택이 확정된 상태라
미결 표시가 남아 있다.

**구현 해석(임시)**: 확정 = 후보 1(런 자체가 투자). 후보 2~5는 폐기/보류.
미결 줄은 삭제 대상. 추가 손실 게이지·부상·시체 런은 구현하지 않는다.

### F5. §5 노드 포인트 소스 서술 중복/충돌

§5 경험치 2종 표: 런 스코프 EXP → "수치노드 포인트 공급".
§5 포인트 소스: "노드 포인트는 런 스코프 캐릭터 EXP가 공급한다 … 이전 가드(장착
장비에서만 포인트 산출)는 폐기". 일관됨. 다만 §5 요소 스코프 목록에는
"장비 창고"가 영속으로, §9 요약에는 장비가 초기화로 적혀 F2와 같은 충돌을 만든다.
→ F2 해소로 함께 해결.

### F6. 보스 출현: 고정(§2) vs 단서 조건(§3)

- §2: "테마의 마지막 던전에 보스가 있다." / "3번째 던전은 중간보스".
- §3: "숨은 단서 수집은 **진짜 보스 출현 트리거 후보**다(확률 시드보다 우선 검토)."

진짜 보스가 "마지막 던전에 항상"인지 "단서를 모아야 출현"인지 미정.
**구현 해석(임시)**: 보스는 마지막 던전에 고정 배치(§2). 단서 트리거는
`// 미결(design §3): 숨은 단서 → 보스 트리거` 스텁만 남긴다.

### F7. 전투 중 "쓰러짐"의 의미가 정의되지 않음

§1/§4/§6.1은 "캐릭터 부상·사망 없음", "쓰러져도 패널티가 누적되지 않는다"만 말한다.
전투 **안에서** HP 0이 된 유닛이 (a) 그 룸에서 행동 불가, (b) 다음 룸에서 부활,
(c) 전투 종료 시 자동 회복 중 무엇인지, 또 룸 클리어 조건과 어떻게 상호작용하는지
정해지지 않았다. 파티 전멸 = 런 종료이므로 "전원 HP 0"은 정의되지만 "1명 0"은 아니다.

**구현 해석(임시)**: 유닛별 `FDownedTag`(행동 불가, 그리드 점유 유지) + 룸 종료 시
정비 지점 규칙으로 회복. 회복 시점·비용은 `// 미결(design §4)`. 전원 downed → 런 종료.

### F8. "런 성공"이 정의되지 않음 → L2 획득 조건이 성립 불가

§6 L2: "획득 조건은 런 성공 또는 보스 돌파다. 실패한 런은 승격을 주지 않는다."
그런데 §2는 런을 "플레이어가 버티는 만큼 길어지는 연쇄"로 정의하고 종료는
전멸뿐이라고 했다 → **끝나는 성공이 없다**. 게다가 §6.2는 인장 획득을
"런 성공, 보스 돌파, 도전과제"로 적는다. "보스 돌파"만 정의 가능하다.

**질문**: L2/인장 지급 트리거를 (a) 테마 보스 클리어, (b) 중간보스 포함 모든 보스,
(c) 도달 깊이 임계값 중 무엇으로 할 것인가? 또 "런 성공"이라는 개념을 폐기할 것인가?

## B. 미결/미정 — 코드에 스텁으로만 남긴 것

### Q1. 이동 AP·스킬 AP 최종 수치와 비용 상한 (§4 미결)

잠정: 이동 AP 1 / 스킬 AP 2 (§4 확정 잠정치). 데이터 파일에서만 바꾸도록 구현.

### Q2. AP 회복·추가 AP 부여 수단 (§4 미결)

구현하지 않음. `// 미결(design §4)`.

### Q3. 이동 거리(칸)와 사거리 수치 (§4 미결)

데이터 값으로만. 그리드는 8x8 확정.

### Q4. 태그 후보 최종 세트와 개수 (§5 2층: 8~12개 제안)

§5 예시 목록(`Projectile/Melee/Fire/Cold/Channel/Summon/Area/Movement/Duration/Trigger`)을
초기 세트로 데이터에 넣되, 개수는 확정 아님 → 데이터에만 두고 코드는 임의 태그를 허용.

### Q5. 승격 조합 목록 (§5 3층)

메커니즘(사전조건 2변형 → 후보 등장, 최초 조합 연출+도감)만 구현. 조합 목록은 데이터 빈 배열 + `// 미결`.

### Q6. 명단 상한(제안 12)·초과 처리·신규 캐릭터 획득 경로 (§6 L1 미결)

상한 값을 데이터로 두고, 초과 시 동작 없음(로그만) + `// 미결`.

### Q7. 자원 최종 이름과 수치(인장 획득량) (§6.2 미결)

§6.2 표의 가칭(파편=런 한정, 인장=계정 영구)을 그대로 구현하되 이름·수치는 데이터.

### Q8. 초기화권 획득 경로와 희소도 (§6 재편 절충 미결)

초기화권 소비 지점(런 중 재분배)만 만들고 획득 경로는 `// 미결`.

### Q9. 드롭 소스별 기대값·어픽스 풀 크기/티어·리롤 비용·이벤트 룸 종류 목록 (§7 미결)

드롭 3계층 구조만 구현. 표는 데이터 빈 배열 + `// 미결`.

### Q10. 저장/이어하기 포맷 (§2 "정비 지점 저장 허용", §6)

이번 슬라이스 미구현. 구현 시 `schema_version` 필수(R17/R28).

## C. 추가로 발견한 서술 공백

### G1. 테마당 던전 개수 미정

§2: "테마 = 던전 여러 개의 묶음", "3번째 던전은 중간보스, 테마의 마지막 던전은 진짜 보스".
마지막 던전이 3번째와 같을 수 있는지(=테마 3던전) 불명. 데이터로 두고 기본 4를 임시값.

### G2. 정비 지점의 "강화 또는 교체 1회"의 대상 범위

§2: "정비(캠프): 강화 또는 교체 1회". 강화 대상(파편 소비처)이 §6.2의 세 선택지
(강화/치료/초기화권)와 어떻게 겹치는지 불명.

### G3. 이벤트 룸 1~2개의 배치 규칙

§3: "이벤트 룸은 전투 룸 사이에 삽입된다" — 3 전투 룸에 2 이벤트면 순서가 미정.

### G4. 런 스코프 EXP 보조 소스 비율

§5: "주 요소는 몬스터 처치. 보조 소스(룸 클리어·이벤트)의 채택 여부와 비율은 미정."
몬스터 처치만 구현(확정), 보조 소스는 `// 미결`.

### G5. 피해 공식 없음

§4는 목표 전투 길이만 있고 데미지/방어 공식이 없다. 데이터 파라미터(공격력·방어력·
계수)를 두고 공식은 `// 미결(design §4): 피해 공식`. 초기엔 `max(1, power - defense)` 잠정.

## 구현 중 추가 피드백 — 프로토타입 자산 (slice 1: 데이터 계층)

**G6. `assets/data/units.json` / `skills.json`의 id는 임시값이다.**
`game-design.md` §6은 캐릭터 명단 상한·획득 경로를 **미결**로 두었고, §2는 캐릭터 이름을
정하지 않았다. 그래서 slice 1은 로더를 실제로 통과시키기 위한 **프로토타입 행**
(`proto_melee`, `proto_ranged`, `proto_cleave`, `proto_guard`, `proto_shot`)만 넣었다.
이는 새 결정이 아니라 스키마 검증용 최소 데이터다. 명단이 확정되면 자산만 교체하면 되고
코드는 바뀌지 않는다(R22). 리뷰 시 이 행들을 "설계 확정"으로 읽지 말 것.

**G7. 로더가 스키마에 없는 키를 거부한다 → 자산에 주석을 쓸 수 없다.**
JSON에는 주석이 없으므로 "이 값은 잠정치"라는 정보를 자산 파일 안에 둘 수 없다.
그 결과 잠정/미결 표시는 **코드의 `// 미결(design §N):` + `// fallback:`** 에만 남고
자산 값 자체에는 남지 않는다. 밸런싱 단계에서 "이 숫자가 확정인지"를 자산에서 알 수 없다는
뜻이다. 대응 후보(미결로 남김): ① `"$comment"` 같은 허용 키를 스키마에 명시적으로 정의,
② 잠정값을 스키마 밖 `docs/design/` 표에 이중 기록. 지금은 어느 쪽도 결정하지 않는다.
