# 던전 런 기획 — 텍스트 프로토타입 (slice 3~4)

이 문서는 `game-design.md`(상위 기획)의 §2 런 구조 · §3 던전과 룸 · §4 전투 · §7 파밍을
**텍스트 프로토타입 범위로 좁힌 구현 기획**이다. 상위 기획과 충돌하면 상위 기획이 이긴다.

슬라이스 분할 (사용자 요청 m01288을 크기 단위로 자른 것):

- **slice 3** = 던전 입장 + 룸 진행 + 몬스터 행동트리
- **slice 4** = 파밍 드롭 + 장비 장착 + 룬 1개 장착

`확정` = 이 슬라이스에서 구현한다. `미결` = 자리만 두고 결정하지 않는다 (구현이 선택한
해석은 `// 미결(...)` + `// fallback:` 주석으로 남긴다).

---

## 1. 런과 던전 (확정 — slice 3)

- 진행 단위는 **던전 1개** (상위 §2 확정, 사용자 결정 m00732). 테마는 난이도·분위기 묶음일
  뿐 진행 단위가 아니다.
- 던전 = **룸 N개를 데이터 순서대로** 진행한다. 룸 정의는 `assets/data/dungeons.json`이며
  코드가 아니다 — 런 생성기가 시드로 룸을 뽑는 단계(상위 §3 가정)로 가려면 룸이 먼저
  데이터여야 한다 (R17/R22).
- 이 슬라이스의 룸 종류는 `monster` 하나. `event` 룸은 스키마에 자리(kind 어휘)만 두고
  **미구현** — 미결: 이벤트 룸 종류 목록(상위 §7 미결).
- 던전 클리어(마지막 룸 승리) → 허브 복귀, `clearedDungeons` +1. 다음 진입은
  `dungeons.json`의 다음 던전. 마지막 던전 다음은 목록 순환 — **미결**: 테마/보스 구분.
- 파티 전멸 → **런 종료** → 허브 복귀. 클리어한 던전 수는 유지되고 던전 진행은 그 던전
  처음부터 (상위 §2 확정).
- **룸 시작 시 파티 상태 = 온전(HP/AP 리셋).** 근거: 상위 §4 "캐릭터 부상·사망 없음"이
  확정이므로 룸 간 부상 누적도 없다 — 리셋이 같은 계약을 코드로 옮긴 것이다.
  미결: 정비(캠프)·자원 유지 여부는 그 슬라이스에서 재검토.
- 조작: 허브에서 `Confirm` = 던전 입장. 런 중 룸 전환은 자동(승리 프레임)이며 텍스트로
  결과가 표시된다. why 조작을 게임 규칙과 분리하는가: 입장/정비 UI는 프레젠테이션이고,
  진행 자체는 승패 상태에 대한 시스템 반응이어야 결정론이 유지된다 (R19).
- 시드: 런 시작 시 `FRunState.seed`를 고정값으로 둔다(0). 근거: 같은 시드 = 같은 런 (R19).
  미결: 플레이어 입력·시간 시드, 시드 노출 UI.

## 2. 몬스터 행동트리 (확정 — slice 3)

- 행동트리 = **순서 있는 규칙 목록**이며 **위에서 첫 일치 규칙 1개만** 실행한다. 유닛은
  `behavior: [ruleId, ...]`(units.json)로 자기 목록을 갖는다. 이 슬라이스 2의 "가장 가까운
  적에게 첫 스킬" 하드코딩을 대체한다.
- 규칙 행은 `assets/data/behaviors.json`: `{id, when, threshold, then}`.
- 조건 어휘(`when`) — 이 슬라이스 확정 집합:
  - `always`
  - `self_hp_at_or_below` — `threshold`는 비율(0~1)
  - `ally_downed` — 아군 중 쓰러진 유닛이 있다
  - `opponent_in_skill_range` — 스킬 사거리 안에 대상이 있다
  - `opponent_count_at_or_above` — 살아 있는 상대 수 (행동 트리 가지치기용)
- 행동 어휘(`then`):
  - `use_first_skill` — 사거리 안의 가장 가까운 상대에게 첫 스킬
  - `move_toward_nearest_opponent`
  - `move_away_from_nearest_opponent`
  - `wait` — 아무것도 하지 않고 턴을 넘긴다
- 판단은 순수 함수(`rules/FBehaviorTree.h`)로, 실행은 `FEnemyTurnSystem`(유일 소비자)만 한다.
  why 분리: 조건·행동 어휘가 늘어도 시스템은 "규칙을 실행"만 하면 되고, 판단은 표 기반으로
  검증할 수 있다 (R12/R22). why 파일명을 바꾸지 않는가: 시스템의 일은 여전히 "적 턴을
  진행시킨다"이고, 무엇을 고를지는 데이터 + 규칙 함수로 빠졌다 (R9: 이름 변경 없이 행동 교체).
- 미결: 조건·행동 어휘 확장(도발·버프·소모품), 규칙 가중치·확률, 2층 트리(규칙 → 하위 트리),
  파벌/기질과의 접합(상위 §5).

## 3. 파밍 (확정 골격 — slice 4)

- 드롭 3계층 (상위 §7): trash(파편) / 어픽스 롤(장비) / 유니크(고정 아이덴티티).
- 드롭 소스 = **룸 승리**. 테이블은 `assets/data/loot.json`: `{id, rolls: [{kind, weight,
  count}]}` — 종류별 가중치는 코드가 아니라 데이터다 (R22).
- 롤은 **시드 결정론**으로 수행한다: `random(seed, counter)` 순수 함수. registry 순회 순서에
  의존하지 않는다 (R16/R19).
- 손실 범위 (상위 §2 확정): 파편·룬·수치노드는 런 스코프 → 전멸 시 소실. **장비는 거점
  창고로 영속**(사용자 결정 m00738) → 런 실패로도 장비를 잃지 않는다.
- 미결: 드롭 소스별 기대값, 어픽스 풀 크기·티어, pity 곡선, 리롤/분해 비용.

## 4. 장비·룬 (확정 골격 — slice 4)

- 장비 슬롯 3종: `weapon` / `armor` / `trinket`. 상위 §5 대로 **스탯 강화는 장비 + 수치노드로만**
  가능하므로 장비가 스탯의 유일한 코드 경로가 된다. `assets/data/items.json`:
  `{id, slot, mods{attack, armor, health, speed}}`.
- 스탯 조회는 **질의 함수 하나**(`rules/FStatQuery.h`): 기본값 = units.json, 여기에 장비 합산.
  피해 공식(`FDamageSystem`)이 이 함수를 쓴다 — 하드코딩 금지 (R22).
- 룬 슬롯 **1개/유닛** (상위 §5 "룬 = 스킬의 동작 변경"): `assets/data/runes.json`
  `{id, effect, value}`. 이 슬라이스 효과 2종: `skill_range_bonus`, `skill_power_multiplier`.
- 장착/해제는 유닛의 컴포넌트 구조 변경이므로 **팩토리 경유** (R5). UI는 텍스트 목록 +
  `Confirm`/`Cancel`.
- 미결: 어픽스 구조, 세트·유니크 효과, 룬 조합·승격(상위 §5 3층 변형), 슬롯 확장,
  거점 창고의 파일 영속(세션 밖 유지).

## 5. 접합 (프로젝트 제약)

- 수치·아이템·룬·룸·행동은 `assets/data/*.json` + `schema_version`. 스키마 검증 실패는
  **부팅 실패**이지 런타임 열화가 아니다 (R19/R22).
- 엔티티 생성·구조 변경은 팩토리에서만, 시스템 간 통신은 typed event(문자열 디스패치 금지),
  텍스트 표시는 `view/` 한 곳에서만 (R5/R3/R26).
- 검증: `scripts/verify-changeability.sh` + `tests/changeability/fixtures/`. 빌드·테스트 실행은
  소유자 몫이다 (`DEV_WORKFLOW.md` §"Builds Are Human-Run").
