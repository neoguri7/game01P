3한 프레임에서 실제로 도는 것

시스템은 서로를 호출하지 않는다 — 같은 프레임의 큐 이벤트로만 이어진다 (R3)

sequenceDiagram

  participant GP as gameplay
  participant V as View

  AB-->>E: FInputState

  GP->>GP: queueFrame 소비 (같은 프레임)

왜 이 모양인가

  • 입력 → 시뮬 → 표시가 한 프레임 안에서 끝난다. 표시가 시뮬을 되먹이지 않는다.
  • 이벤트는 typed만 쓴다. 문자열 디스패치 없음 → 문자열 키 상태 가방도 없음 (R23/R27).
  • 프레임 순서는 FGameplayServices::RegisterSystems에 주석과 함께 한 곳에만 있다.
  • 이 순서를 깨면 그 자리에서 검출된다 — R3 이벤트 순서 규칙이 fixture로 고정됨.

6전투 1턴이 지나는 경로

플레이어와 몬스터가 같은 요청 경로를 쓴다 — 합법성 판정이 한 곳뿐이다

포인트

  • 등록 순서: Initiative → TurnStart → GridMove → PlayerCommand → EnemyTurn → SkillResolve → Damage → Outcome → TurnEnd → BattleLog → RunProgression.
  • 거부는 FSkillRejectedEvent로 돌아오고 사유가 문장으로 로그에 남는다. 조용한 실패가 없다.
  • 몬스터가 고르는 것은 데이터(behaviors.json) + 순수 함수. 실행하는 것만 FEnemyTurnSystem.
  • 피해 적용과 승패 판정이 분리돼 있다 — 피해 공식이 확정되면 FDamageSystem 한 곳만 바뀐다.
